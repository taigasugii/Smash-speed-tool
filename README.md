# smash-speed

バドミントンのスマッシュ動画から、シャトルの **初速（インパクト直後の速さ）** と **平均速度** を推定する研究用ツール。
240fps の高速度撮影に加え、一般的なスマホ動画（30 / 60fps）でどこまで正確に推定できるかを検証する仕組みを含む。

フレーム間の差分ではなく、**空気抵抗つきの運動方程式を軌道全体に当てはめ**、打点時刻での速さを求める。
低 fps では打点直後の数十 ms に大きく減速する区間が写らないため、差分では初速を大きく過小評価する（下の「合成データでの検証結果」）。

## 処理の流れ

```
動画読み込み（ffprobe, VFR 対応）→ キャリブレーション（コート・ネットをクリック → 3x4 投影）
→ シャトル検出（背景差分ベースライン / TrackNetV3。打つ人・着地点がわかれば、打点から出る軌道の総当たりで選ぶ）
→ 打点時刻（打球音・軌道の交点・打者の位置）
→ 3次元化（鉛直な飛行平面との交点 / 2台の三角測量）→ 運動方程式の当てはめ（再投影誤差 + Huber 損失）
→ 初速・平均速度・到達時速度と 95% 信頼区間 → CSV・グラフ・オーバーレイ動画
```

途中結果（`calibration.json`・`detections.csv`・`events.json` など）はすべて保存し、どの段階からでもやり直せる。

## GUI で使う（おすすめ）

エクスプローラーで **`smash-speed-gui.bat` をダブルクリック** すると、ブラウザでアプリが開く（コマンドの入力は不要）。
この PC の中だけで動くサーバー（`http://127.0.0.1:8765`）を使うので、動画は外に送られない。ブラウザを閉じて 2 分たつと自動で止まる（左下の「アプリを終了」でも止まる）。

左のメニューの手順を上から順に進める。各画面の上に、その画面でやることが書いてある。

| 手順 | 画面でやること |
|---|---|
| ホーム | 「動画を選ぶ…」で動画を開く。スロー動画は実際の撮影 fps を入れる。はじめてなら「お試し用の動画を作って開く」で一通り試せる |
| 1 スマッシュを選ぶ | 「打球音を探す」で時間軸にオレンジの線が出る → 動画を動かして「今の位置を開始に / 終了に」 |
| 2 コートを合わせる | ①上から見たコートの図で、カメラの位置と打つ人の半面をクリック → ②図が「カメラから見た向き」に回り、次にクリックする点が赤く点滅する。点の名前（例：手前・右のショートサービスラインの端）と、線のどこを狙うかの図が出るので、その通りに動画の上をクリックする。映っていない点は S でとばす。5 点目からは計算が始まり、残りの点の予想位置が点線の丸で出る（画面の外の点は自動でとばす）。**自動で合わせる**：右下の図でコートの角を選び、動画の上でその角を **1 点だけ**（ルーペで正確に）クリックして「この 1 点から自動で合わせる」を押すと、床のラインの向き（消失点）からカメラの向きを求め、手順 ① のカメラの位置を手がかりにコートのラインに合わせて残りの点を自動で置く（20〜40 秒）。1 点で合わないときは、床の角を 4 点（なるべく離れた 4 点。だいたいの位置でよい）クリックして「残りの点を自動で合わせる」を押すと、コートのラインに吸い付けて残りの点を自動で置く（水色の「自」。10 秒ほど）。ずれた点だけ選んでクリックし直す。ラインで確かめられなかったクリック点は名前で知らせるので、ルーペで置き直す → ③黄色の線（コートのライン）が実際のラインに重なっているかを見て保存 |
| 3 打つ人と着地点 | 動画の上で、打つ人の足元と着地点の床をクリック。検出する範囲は自動で絞り込むので、ふつうは囲まなくてよい（それでも選手の動きなどを誤検出するときだけ「検出する範囲」を四角で囲む） |
| 4 解析する | 準備の確認（緑のチェック）を見て「解析する」。進み具合は画面の下に出る |
| 5 結果 | 初速・平均速度・着地直前の速さと、結果の信頼性（画面上のずれ・使ったコマ数・打った瞬間の求め方）、グラフ、結果を描き込んだ動画 |

「いちばん速いスマッシュ」では、動画の中のスマッシュをまとめて解析し、速い順に並べる（手順 2 のコート合わせが済んでいること）。
①「候補を探す」で、打球音ごとに直後のシャトルを探してだいたいの初速を出す（4K 30fps・2 分の動画で 1〜2 分）→
②速そうな候補（最初から 8 個に印がつく）の「確認する」で、推定した打つ人の足元・着地点を動画の上で直す →
③「選んだ候補を詳しく解析する」で通常の解析を行い、速い順に並べる（1 本 5〜30 秒）。
①の値は打つ人・着地点を推定したものなので ±30% ほどずれる。順位は③で決め、1 位と 2 位の 95% の範囲が重なるときは「差は誤差の範囲内」と表示する。450 km/h を超える結果は順位から外す。

「ショットの一覧」では、動画の中のすべてのショット（スマッシュ・クリア・ドロップ・ドライブ・ロブ・ネット・プッシュ・サーブ）を
種類と初速つきで並べる（手順 2 のコート合わせが済んでいること）。動画全体か区間を選んで「解析を始める」を押すと、進み具合が
画面の下に出る（4K 30fps の 20 秒で約 70 秒）。種類ごとの本数・平均と最高の初速のカードを押すとその種類だけに絞り込め、
表は時刻の順と速い順に並べ替えられる。表の行を押すと、打った少し後の場面に見つけたシャトルと計算した飛び方を重ねた画像と、
コートを上から見た飛び方（打った所・落ちた所）が出る。場面は「前のコマ」「次のコマ」・スライダー・キーボードの ← → で、
打つ 0.2 秒前から次の打球までを 1 コマずつ送れる（そのコマのシャトルと、計算した飛び方のその時刻の位置に印が付く）。一覧は CSV で保存できる。
「いちばん速いスマッシュ」と「ショットの一覧」は、それぞれの画面のボタンから行き来できる。種類は決まりに沿って分けた目安で、実際の試合の動画での精度はまだ確かめていない。
正しい種類が分かるショットは、表の「正しい種類」の欄か、行を押して出る詳しい所のボタン（キーボードの 1〜8 でも）で選ぶ。
「選んだら次のショットへ進む」を入れておくと、続けて付けられる。選んだ種類は出力の場所の `shot_labels.csv`（動画をまたいで 1 つ）に残り、
解析し直しても同じショットに付き直す。表の上に、選んだ本数（この動画・全部）と、決まりの判定が合っていた割合が出る（ROADMAP B6、学習は B7）。

ほかに「結果の一覧」（これまでの全結果と集計表）、「研究ツール」（正解ラベル付け・合成データ・疑似低 fps 動画・精度検証・TrackNetV3 の学習データ）、「設定」（保存先・上書き用の設定 YAML）がある。
動画の上では、マウスホイールで拡大、右ドラッグ（またはスペース＋ドラッグ）で移動。クリックする画面ではカーソルの近くにルーペが出る。

> PowerShell で `Activate.ps1` が「スクリプトの実行が無効」と言われる場合も、GUI（.bat）はそのまま使える。
> コマンドを使うときは `smash-speed` の代わりに `.\.venv\Scripts\smash-speed.exe` と書けば有効化は不要。

## セットアップ（Windows）

前提：Python 3.11 以上（開発は 3.12）、ffmpeg / ffprobe。

```powershell
# ffmpeg（未導入の場合。インストール後はターミナルを開き直す）
winget install --id Gyan.FFmpeg -e

# 仮想環境
cd smash-speed
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -e ".[dev]"

# 任意：深層学習（TrackNetV3 の推論・学習。CPU 版で可）／姿勢推定（MediaPipe）
python -m pip install -e ".[dl]"
python -m pip install -e ".[pose]"

# 任意：GPU での推論（onnxruntime-directml。約 33 MB）。速さの確かめ方は docs/gpu.md
python -m pip install -e ".[gpu]"
python -m smash_speed.accel --bench

# テスト（合成データで全モジュールを確認。1 分ほど）
pytest
```

ffmpeg が PATH にない場合も、winget の既定のインストール先は自動で探す。別の場所なら `configs/default.yaml` の `video.ffmpeg` / `video.ffprobe` に書く。

## 自宅のデスクトップで動かし、スマホ・ほかの PC から使う

解析・学習は自宅のデスクトップで動かし、画面だけをスマホやノート PC から操作できる。
つなぐのは [Tailscale](https://tailscale.com/)（自分の端末どうしだけをつなぐ VPN。個人利用は無料）で、
インターネットには公開しない。

1. **デスクトップの準備**：上の「セットアップ」と同じ（`git clone https://github.com/taigasugii/Smash-speed-tool.git`）。
   動画・キャリブレーション（`outputs/*_calibration.json`）・学習データは Git に入らないので、USB メモリや
   OneDrive などで `outputs/` と動画を移す。
2. **Tailscale**：デスクトップ・スマホ・ノート PC のそれぞれに Tailscale を入れ、**同じアカウント**でログインする。
3. **起動**：デスクトップで `smash-speed-remote.bat` をダブルクリックする。初回だけ合言葉（8 文字以上）を決める。
   Windows のファイアウォールの確認が出たら「プライベート ネットワーク」だけ許可する。
   最後に、スマホで開くアドレス（`http://100.x.x.x:8765/`）が表示される。
4. **スマホ・ノート PC**：Tailscale をオンにして、表示されたアドレス（または `http://デスクトップの名前:8765/`）を
   ブラウザで開き、合言葉でログインする（30 日間はログインしたまま）。

離れた端末から使うときの違い：

- 動画は「デスクトップの動画を選ぶ」（デスクトップのフォルダをたどる）か、「この端末の動画を送る」
  （スマホで撮った動画をデスクトップの `data/uploads` に送る）で開く。
- 解析は全部デスクトップで動く。スマホを閉じても止まらず、あとで開き直せば結果を見られる。
- 「アプリを終了」の代わりに「ログアウト」が出る（離れた端末からは起動し直せないため、終了はデスクトップで行う）。
- 状態（開いている動画・コート合わせの途中の点）は全端末で共通。同時に 2 台で操作しないこと。

安全のため：Tailscale の端末（100.64.0.0/10）とデスクトップ自身以外からの接続は、合言葉があっても断る。
合言葉は変換した値だけを `outputs/remote_access.json` に保存する。合言葉を変えるには
`python -m smash_speed.webapp --set-passphrase`（ログイン済みの端末はすべてログアウトされる）。
同じ端末から 10 分の間に 5 回まちがえると、10 分ほど受け付けない。

## 自律開発エージェント（Badminton Analytics への拡張）

デスクトップで Claude Code を無人で動かし、`agent/ROADMAP.md` の課題を 1 つずつ実装していきます。
課題は、すべてのショットの速度と種類、ラリーの統計、選手の動き、フォーム・姿勢の解析などです。

- 毎晩 0:00〜12:00 は自動で動きます。それ以外の時間は、GUI の「開発エージェント」から 1 回ずつ動かせます。
- 変更は品質チェックを通ったものだけが `agent/dev` ブランチに入り、main への PR にまとまります。マージは人が行います。
- 準備と使い方は [agent/README.md](agent/README.md) にあります。

## 使い方

### 0. まず合成データで通しで動かす

```powershell
smash-speed synth --out outputs/demo --speed 80 --fps 240
smash-speed analyze --video outputs/demo/synthetic.mp4 --calib outputs/demo/calibration.json `
    --audio outputs/demo/synthetic.wav "--hitter=-4.8,-0.86" "--landing=5.16,1.0" --out outputs/demo/analysis
```

`outputs/demo/truth.json` に正解（初速 288 km/h、打者・着地点の座標）がある。

> **負の座標の渡し方**：`--hitter -4.8,-0.86` はオプションと誤認されるので、`"--hitter=-4.8,-0.86"` のように `=` でつなぐ。

### 1. スマッシュを探す（長い動画の場合）

```powershell
smash-speed onsets --video IMG_4521.MOV > onsets.csv      # 打球音の候補時刻と強さ
```

### 1b. 動画の中のスマッシュをまとめて解析する（いちばん速いものを探す）

```powershell
# ① 候補探し：打球音 → 直後のシャトル → だいたいの初速（打つ人・着地点は推定）
smash-speed find-smashes --video IMG_4397.MOV --calib calibration.json --out out/IMG_4397_smashes
# （必要なら out/IMG_4397_smashes/candidates.json の hitter / landing を直し、confirmed を true にする。GUI なら画面で直せる）
# ③ 選んだ候補（selected）を詳しく解析して速い順に並べる → ranking.csv
smash-speed analyze-smashes --batch out/IMG_4397_smashes
```

- 動画は縮小しながら 1 回だけ読み、打球音の前後（−0.25〜+0.85 s）だけを検出に回す。
- 打点は「画像上の軌道を打った瞬間まで戻した位置が、高さ 2.5 m にある」として決め、飛ぶ向きは ±30° を探す。
  カメラが打つ人の後ろ（視線が打点に向かって急な角度）なら、打つ人の推定は実際の足元から 0.5 m 前後に収まった。
  カメラが横・低い位置（視線が浅い）だと奥行きがずれやすいので、②の確認が欠かせない。
- 隣のコートの音・打点がコートの外になるもの・ありえない速さになるものは候補から外す（一覧の「すべての打球音」で理由を見られる）。
- ③では `ranking.csv` と同じ結果を、ショットの形（`shots.csv`、下の「ショットとラリーのデータ形式」）でも書き出す。
  前に解析した出力先からは `python -m smash_speed.shots out/IMG_4397_smashes` で書き出せる。

#### ショットとラリーのデータ形式（`shots.csv`・`rallies.csv`）

すべてのショット・ラリーの解析（ROADMAP の B・C）はこの形で結果を出す（`smash_speed/shots.py`）。
1 行 1 本、分からない値は空欄、文字コードは BOM 付き UTF-8（Excel でそのまま開ける）。

| `shots.csv` の列 | 中身 |
|---|---|
| `t_hit_s` | 打った時刻（映像の時刻）[s] |
| `side` | 打った側。`h` = x < 0 の側、`o` = x > 0 の側（座標系とランドマークの名前と同じ） |
| `shot_type` | `smash` `clear` `drop` `drive` `lob` `net` `push` `serve` `unknown` |
| `speed_kmh`, `speed_ci_low_kmh`, `speed_ci_high_kmh` | 初速と 95% 信頼区間 [km/h] |
| `hit_x_m`, `hit_y_m`, `hit_z_m` | 打点 [m] |
| `land_x_m`, `land_y_m`, `t_land_s` | 着地点 [m] と着地した時刻 [s] |
| `v0_x_mps`, `v0_y_mps`, `v0_z_mps`, `terminal_velocity_mps` | 打点での速度と終端速度。軌道はこれと打点から描き直す（`Shot.trajectory`） |
| `confidence` | 信頼度 0〜1。いまは「1 −（初速の信頼区間の幅 ÷ 初速）」 |
| `rally_id`, `index_in_rally` | 属するラリーと、その中で何本目か |
| `source`, `ref`, `note` | どの解析から来たか、元の結果の場所、メモ |

`rallies.csv` は `rally_id`・`t_start_s`・`t_end_s`・`n_shots`・`winner_side`（得点した側）・
`end_reason`（`in` `out` `net` `fault`）・`score_h`・`score_o`（ラリーの後の得点）・`note`。
知らない列は読み飛ばすので、表計算ソフトで列を足しても読み込める。

### 2. キャリブレーション（カメラごとに1回）

```powershell
smash-speed calibrate --video smash01.mp4 --time 12.0 --out calib.json
```

ウィンドウに1フレームが表示され、右上の上面図で **赤く光るランドマーク** を順にクリックする（映っていない点は `s` でスキップ）。

| 操作 | キー |
|---|---|
| 点を置く | 左クリック |
| スキップ / 元に戻す | `s` / `u`・BackSpace |
| 前 / 次のランドマーク | `b` / `n` |
| 点の微調整（刻み 0.25 / 1 / 5 px） | 矢印キー（刻みは `[` `]`） |
| 拡大縮小・移動 | ホイール・`z` `x`・右ドラッグ・`r` |
| 推定して再投影を重ね描き | `c` |
| 保存 / 中止 | Enter / Esc |

`c` を押すとコートのラインとネットが重ね描きされ、点ごとの再投影誤差がコンソールに出る（5 px を超える点は赤丸と警告）。
同じ位置に固定したカメラの別の動画には `calib.json` をそのまま使える。確認は
`smash-speed check-calib --video smash02.mp4 --calib calib.json --out check.png`。

- クリックの座標を JSON（`{"ランドマーク名": [u, v], ...}`）で渡して GUI なしでも推定できる（`--points pts.json --no-gui`）。
- レンズの歪みが大きい（超広角など）場合は `--k1`、またはチェッカーボードで内部パラメータを求めて `--intrinsics` で渡す
  （`smash_speed.calibration.solve.intrinsics_from_checkerboard`）。

### 3. 解析

```powershell
smash-speed analyze --video smash01.mp4 --calib calib.json --start 61.8 --end 62.8 `
    "--hitter=-4.5,-0.8" "--landing=4.0,1.2" --out outputs/smash01
```

| 入力 | 説明 |
|---|---|
| `--start` `--end` | 解析区間 [s]。打点の少し前から着地まで（1 本のスマッシュ） |
| `--capture-fps` | 実際の撮影 fps。スロー動画が 30fps として記録されている場合などに指定（時刻を実時間に換算） |
| 飛行平面 | `--hitter` `--landing`（コート座標 [m]）、`--hitter-px` `--landing-px`（画像座標）、`--plane-gui`（クリック）、`--plane plane.json` のいずれか。省略すると格子探索で推定（試験的） |
| 打点時刻 | 既定 `--impact-method auto`：打球音 → 打点前の軌道との交点 → 打者の位置 → 最初の検出 の順。`--impact-time` で手動指定も可 |
| `--detections` | 既存の検出 CSV（TrackNetV3 の結果やアノテーション）を使う |
| `--ci bootstrap` | 信頼区間をブートストラップで出す（既定はヤコビアン） |
| `--force` | 保存済みの途中結果を使わず作り直す |

出力（`--out`）：

| ファイル | 内容 |
|---|---|
| `result.csv` | 初速・平均速度（移動距離 / 直線距離）・到達時速度・減速率（m/s と km/h）、95% 信頼区間、フレーム間差分による参考値、使用フレーム数、fps、モード |
| `speed_time.png` | 時刻と速さ（物理モデル・フレーム間差分・初速の信頼区間） |
| `trajectory.png` | 3次元軌道の側面図・上面図 |
| `image_fit.png` | 画像上の検出と当てはめた軌道の比較 |
| `overlay.mp4` / `overlay_web.mp4` | 検出位置・当てはめた軌道・初速を描き込んだ動画（`_web` はブラウザや Windows の標準プレーヤーで再生できる H.264 版） |
| `observations.csv` | 当てはめに使ったシャトルの位置（コマ番号・時刻・画像座標） |

#### 打つ人の位置を手がかりにしたシャトルの探し方

打つ人の足元・着地点（飛行平面）と打球音がわかっているとき（GUI の手順 3 を済ませたとき）は、次の 3 つを自動で行う
（`smash_speed/detection/guided.py`。設定は `detection.auto_roi` / `physics_search` / `redetect`）。

1. **検出する範囲の自動化**：打つ人の足元の 1 m 後ろから着地点の 1 m 先まで、床〜高さ 4 m、飛行平面の左右 0.8 m（先へ行くほど広げる）の
   空間を画像に投影し、その中だけで検出する（「検出する範囲」を指定したときはそちらを使う）。
2. **打点から出る軌道の総当たり**：打球音の時刻（カメラまでの音の遅れを引いたもの）に、打点（足元の少し前・高さ 2.5 m 前後）から
   打ち出した軌道を、初速 15〜115 m/s・打ち出し角・向き・打点の位置を変えて約 3 万本作り、各コマの「シャトルらしさ」の地図
   （3 フレーム差分のうち、小さな点・まっすぐな細い残像の形のもの）の上を最も強く通るものを選ぶ。
   選手・観客・ラケットの動きは打点から出る物理的な軌道に乗らないので選ばれず、シャトルが人と重なって 1 つの塊になったコマがあっても
   軌道全体で判断できる。従来の選び方の軌道がこの軌道とほぼ重なるときは、従来の軌道を使う（打った直後のラケットが混じりにくいため）。
3. **漏れたコマの探し直し**：当てはめた軌道の予測位置のまわりを元の解像度で探し直し、最初の検出で漏れたコマを補う
   （補った方が軌道に合わなければ使わない）。

また、視線と飛行平面の角度が 20° 未満（打つ人の真後ろ・真正面から撮った）のときは、飛行平面に縛らずに 3 次元の軌道を当てはめる
（`physics.free_below_graze_deg`）。この角度では、足元・着地点のクリックが横に 10〜20 cm ずれるだけで、平面との交点＝奥行きが大きく変わるため。

複数本の集計：`smash-speed summarize --results outputs --out summary.csv`

## 撮影ガイド

精度に効く順に：

1. **音声を録る**（打球音で打点時刻が 2 ms 程度で決まる）。打点時刻の誤差は初速の誤差に直結する（初速 80 m/s 付近で 1 ms ≈ 1.3 m/s）。
2. **コートの側方・高い位置（2〜4 m）から、飛行平面をほぼ正面に見る**。カメラは飛行平面から 6〜10 m 離す。
   ネット際の低い位置から斜めに見ると、平面との交点の誤差が大きくなる。
3. **三脚で固定し、ズームしない**（キャリブレーションを使い回せる）。キャリブレーション用に、ネットポストの上端・根元とコートの角が
   なるべく多く映るようにする（高さのある点を最低 1 つ）。
4. **シャッター速度を速く**（1/1000 s 以上が目安）。低 fps・長い露光ではシャトルが薄く長い残像になり、
   打点直後の数フレームが検出できないことがある（合成データで確認）。
5. 可能なら 240fps のスロー撮影。スロー動画を書き出すと 30fps として記録されることがあるので `--capture-fps 240` を指定する。
6. 超広角（0.5x）は歪みが大きいので、可能なら 1x を使う。使う場合は `--k1` を試す。

## 精度に影響する仮定（結果を解釈するときの注意）

| 仮定 | 影響（合成データでの例） | 対策 |
|---|---|---|
| **平面拘束**：シャトルは打者の足元と着地点を通る鉛直な平面内を飛ぶ | 平面の向きが 1° ずれると初速が約 5%、位置が 10 cm ずれると約 3% ずれる | `refine_plane`（既定で有効）で平面の向き・位置も再投影誤差から推定する。2° / 0.2 m のずれでも補正後は数 % |
| **空気抵抗**：速度の2乗に比例し、終端速度 v_t は一定（既定 6.7 m/s） | v_t はシャトルの種類（羽根 / ナイロン）・気温・気圧で変わる | `estimate_terminal_velocity: true` でデータから推定（240fps で軌道が長く写っている場合） |
| **打点時刻** | 80 m/s では 1 ms のずれ ≈ 1.3 m/s | 打球音（伝搬遅れ＝カメラまでの距離 / 343 m/s を自動補正）、軌道の交点、打者の位置。信頼区間に打点時刻の不確かさを加算 |
| **音と映像の同期** | スマホの音声と映像の内部的なずれは機種による | 必要なら `--av-offset` で補正（手を叩く様子を撮って確認できる） |
| **打点直後のシャトルの反転（フリップ）** | 打点後 数 ms の過渡的な挙動はモデル化していない | 初速は「当てはめた軌道を打点時刻に外挿した速さ」と定義する |
| **平面の補正が効く条件** | 平面の向き・位置の補正は、強い減速による軌道の曲がりを手がかりにする。終端速度に近い落下（高いクリアの落ち際など）では、ほぼ等速直線運動になり「近くて遅い」と「遠くて速い」を区別できない | スマッシュの序盤には有効。落下中のシャトルを解析するときは `refine_plane: false` にして平面を正しく与える |
| **カメラモデル** | 歪みを無視すると画像の端で誤差が出る | `--k1`・チェッカーボード |
| **観測時刻 = 露光の中央** | ローリングシャッター（行ごとの時刻のずれ）は無視している | 高速シャッターで影響は小さくなる |

## 合成データでの検証結果

`smash-speed validate --synthetic --n 100`（初速 50〜100 m/s、検出ノイズ 1.5 px、検出漏れ 10%、飛行平面のずれ 2° / 0.2 m を
`refine_plane` で補正、打球音による打点時刻の誤差 σ = 2 ms）。初速の MAPE [%]：

| 方法 | 30fps | 60fps | 120fps | 240fps | 30fps のバイアス |
|---|---|---|---|---|---|
| フレーム間差分（最初の区間） | 36.0 | 22.6 | 12.9 | 6.9 | -98 km/h |
| 物理モデル + 打球音 | 4.4 | 4.4 | 3.9 | 3.2 | ±0 km/h |
| 物理モデル + 打者の位置 | 9.0 | 8.1 | 6.0 | 5.6 | +5 km/h |
| 物理モデル + 最初の検出 | 17.1 | 8.0 | 4.9 | 2.9 | +2 km/h |

物理モデル + 打球音の 95% 信頼区間の被覆率：0.94〜0.97（名目 0.95）。

- **物理モデル + 打球音** は 30fps でも 240fps とほぼ同じ精度で、誤差の大半は打点時刻（2 ms）と飛行平面のずれによる。
- **フレーム間差分** は、低 fps ほど初速を大きく過小評価する（30fps で −36%）。線形補正（前半 50 本で学習・後半で評価）でも 30fps では 12% 残る（補正係数は撮影条件ごとに違うので使い回せない）。
- 音声がない場合、最初の検出から打点を推定すると 30fps で 17%。打者の位置（打点 = 足元の 0.3 m 前、σ 0.4 m）から推定すると 9% に改善する。
- 240fps では最初の検出から推定しても打点時刻の誤差が ±2 ms 程度に収まるため、打球音と同程度以上の精度になる。

> これは合成データ（仮定どおりの理想的な条件）での結果で、実データの精度は 240fps 実動画での検証（`validate --dataset`）で確かめる必要がある。

### すべての打球を見つける（`smash_speed/hits.py`）

動画全体のシャトルの検出結果（と、あれば打球音）から、すべての打球の時刻と打った側を出す（`find_hits`）。

- 軌道の向きが変わる所：ある時刻の前と後の数点（約 0.1 秒）に 2 次式を当てはめ、その時刻での速度の差が
  検出位置のばらつきと速さから見て大きすぎる所を打球とする。時刻は、前後の式がいちばん近づく時刻。
  止まった所（床に落ちた）は除き、検出が途切れた間に向きが変わっていればその間に打球を置く。
- 打球音：軌道の変化の近く（80 ms 以内）にあれば時刻は音にする。音が届くまでの遅れは、音と軌道の両方がある
  打球から見積もって引く。軌道の変化のない音は、シャトルが見えていて向きが変わっていなければ捨てる（隣のコートの音など）。
- 画面の端から出入りした所・検出の始まりは弱い手がかり（音があるときは、音で確かめられたものだけ打球にする）。
- 打った側は、次の打球までにシャトルが画像上で動いた向きをコートの x 軸と比べた票と、「1 ラリーの中ではふつう交互」から

### ショットごとの軌道と初速（`smash_speed/shot_fit.py`）

見つけた打球の時刻で動画全体の検出結果を 1 本ずつの飛行に分け、スマッシュと同じ物理モデル（空気抵抗つき）を
すべてのショットに当てはめる（`fit_shots`）。カメラ 1 台では奥行きが決まらないので、飛行平面を次の順に決める。

1. コートの x 軸に近い平面を粗い格子（ネットを横切る位置 3 通り × 向き 3 通り）で試して当たりをつけ、
   平面を大きく動かせるようにして当てはめる。長く飛ぶショットは、画像上の曲がり方から奥行きが決まる。
2. 打点の時刻を、前のショットと次のショットの軌道が画像上で交わる時刻に直す（打球音は届くまでの遅れ、
   軌道の向きの変化はコマの間隔の分ずれる。スマッシュでは 1 ms のずれが初速の約 2% になる）。
3. 打点は「前のショットの終わり」と「このショットの始まり」の同じ点なので、両方から打点を出してつなぎ、
   飛行平面を「打点 → 次の打点（最後は着地点）」にして当てはめ直す（2〜3 を 2 回）。

### ショットの種類の判定（`smash_speed/shot_types.py`）

当てはめた軌道を床まで延ばし、初速・打ち出し角・打点の高さ・軌道のいちばん高い所・ネットの上を通る高さ・
着地点の深さ（相手側のネットからの距離。打ち返されたショットは「誰も打たなかったら落ちた所」）を出して、
次の順に決める（`classify_features`。しきい値は `RuleThresholds`。分類は ShuttleSet を 8 種類にまとめたもの）。

1. ラリーの最初のショット → サーブ
2. 打点が 1.95 m 以上（頭より上で打った）：下向きで 36 m/s（130 km/h）以上 → スマッシュ、
   着地点が 3.8 m より深い → クリア、それ以外 → ドロップ
3. それより低い打点：着地点がネットから 1.75 m 以内 → ネット、4 m より深く、28° 以上で打ち出すか 3 m 以上
   上がる → ロブ、それ以外の低い軌道は 20 m/s（72 km/h）以上 → ドライブ、遅ければ → プッシュ

`classify_shots` で `Shot` の列に種類を入れる（決まっている種類はそのまま）。
`python -m smash_speed.shot_types shots.csv` で種類を入れた `shots_typed.csv` を書き出し、
`python -m smash_speed.shot_types --bench` で合成ラリーの混同行列を出す（`--truth` は正解の軌道から）。

30 fps の見落とし 3 本は、速い低い打ち合い（プッシュ → ドライブ → プッシュ）が続いた所。種類の間違いは

**シャトルらしい軌道の絞り込み**（`shuttle_tracks`・`TrackFilter`）：実動画では、選手・ラケット・ほかのコートの人の動きも
軌道になる（IMG_4397 の 20 秒で約 1150 本）。検出は重なった軌道も残して出し、次の条件をすべて満たす軌道だけを残してから
1 コマ 1 点にする。止めるときは `--all-tracks`。

| 条件 | 値 | 落とすもの |
|---|---|---|
| 点の数・長さ | 5 点以上・0.13 秒以上 | 短い切れ端 |
| 画像の上の速さ（1 コマの移動の中央値） | 画像の幅の 1.2 倍 / 秒 以下 | 別々の物の間を飛び移った軌道（実動画で 1.5〜6） |
| 点の広がり | 画像の幅の 3% 以上 | 止まっている物 |
| 視線がコートの空間（外側の線から長さ方向 2 m・幅方向 1.5 m 広げ、高さ 12 m まで）を通る点 | 8 割以上 | 隣のコートの奥・客席など |
| コートの空間のいちばん奥にあるとしたときの速さ | 3 m/s 以上 | 人の歩き・手足の動き |

残った軌道どうしが同じ時間に重なったら（`select_tracks`。0.07 秒までの重なりは同じシャトルの続きとして許す）、
重ならない組で点の数の合計がいちばん多いものを選ぶ。画面の左右の端（幅の 2%）から始まった軌道は点を半分に数える
（ラリーのシャトルは打点か画面の上から入ってくる。左右の端から入ってくるのはほとんど隣のコートのシャトル）。
以前は 1 コマずつ確からしさの高い方を選んでいたので、隣のコートのシャトルが打球の前後の数コマを奪い、
打球の時刻と打った側を間違えていた。同じコマに 2 本残ったら確からしさの高い方。

合成ラリーの動画では軌道は 1 本も落ちない（テストで確かめている）。当てはめはショットごとに互いに関係しないので、
CPU の数 − 1（16 まで）のプロセスで並べて動かす（結果は 1 つずつ計算したときと同じ）。

**打点の時刻**（`shot_fit.audio_hit_times`）：打球音のあるショットは、スマッシュの解析と同じく
「打球音の時刻 − 打点からカメラまでの距離 ÷ 音速」を打点の時刻にする。ただし前後の軌道が交わる時刻と 4 ms 以内で
合っていれば交わる時刻のまま（合成ラリーではこの方が初速が合う）。実動画の 30 fps では打球の瞬間の検出が抜けて
交わる時刻が 5〜11 ms ずれ、スマッシュでは初速が 2 割ほど変わる。
当てはめに失敗しているショット（画像の上のずれが画像の幅の 1% 超・600 km/h 超）は、打点をつないだ当てはめ直しの
繰り返しの上限を下げる（1 本 20〜50 秒 → 5〜9 秒。飛ばすと、つなぎ直しで救われるショットを失う）。

実動画（IMG_4397、4K 30 fps、A1 の基準のキャリブレーション、80〜100 s）での変化：

|---|---|---|---|
| 残った軌道 | 70 本（1 コマ 1 点にした後） | 37 / 1151 本 | 25 / 1151 本 |
| シャトルが見えたコマ | 600 / 602 | 399 / 602 | 384 / 602 |
| 打球 | 37 本 | 25 本 | 23 本 |
| 画像の上のずれが 5 px 以内の当てはめ | 1 / 18 本（80〜90 s） | 13 / 25 本 | 13 / 23 本 |
| 速さが出たショット（600 km/h 以下・ずれが画像の幅の 1% 以内） | 11 / 18 本（80〜90 s。ずれの条件を足す前の数え方） | 15 / 25 本 | 20 / 23 本 |
| 基準のスマッシュ 82.1 s（340 km/h） | 647 km/h（失敗） | 163 km/h | 342 km/h（+1%） |
| 基準のスマッシュ 91.2 s（345 km/h） | 打球なし | 367 km/h（+6%） | 328 km/h（−5%） |

94.9 s は、当てはめた打点が基準の打点（x = −2.84 m）より 3 m ほど後ろ（−5.62 m）に出て、飛ぶ距離が長い分だけ速く出る。

### ラリーの区切り（`smash_speed/rallies.py`）

となり合う 2 本のショットの間ごとに、次の順で区切るかを決める（`split_rallies`）。

1. 8 秒より空いた → 区切る（`note` に「終わり：間隔」）。
2. 前のショットの当てはめた軌道が、次の打球より 0.3 秒以上前に床に着く → 誰にも打たれずに落ちたので区切る
   （「終わり：着地」）。打ち返されたショットは床に着く前に打たれるので、着地はその後になる。初速が出なかった
   （当てはめに失敗した）ショットの軌道は使わない。
3. 3 秒より空き、その間シャトルがほとんど見えていない（見えたコマが 4 割未満）→ 区切る。見えていれば、
   打球を見落としただけでラリーは続いているとみなす。

ラリーの終わりの時刻は最後のショットの着地の時刻（なければ最後にシャトルが見えた時刻）。最後のショットの着地点から
終わり方（`end_reason`：相手のコートの中 `in`・外 `out`・ネットを越えない `net`）と得点した側（`winner_side`）を決める
（線から 10 cm 以内は `note` に「線の近く」。入・出はダブルスの線で決める。`RallyOptions(singles=True)` でシングルス）。
得点（`score_h`・`score_o`）は、動画の始まりの得点が分からないので空欄のまま。選手の動き（打った後に止まる・
サーブの位置に戻る）は、選手の検出（ROADMAP D1）ができてから足す。

続けて打った合成ラリー（`synth_rally.make_session`。前のラリーのシャトルが落ちてから休んで、得点した側がサーブ）での
結果（`python -m smash_speed.rallies --bench`。30 fps、区切りは正解と組になった打球の間で数える）：

| 休み（着地から次のサーブまで） | 流れ | ラリー | 区切りの再現率・適合率 | 打球の間隔だけ（今までのやり方）の再現率 |
|---|---|---|---|---|
| 1〜8 秒 | 正解のショット（着地の時刻に 0.1 秒のずれ） | 120 | 1.000・1.000 | 0.920 |
| 1〜8 秒 | 検出 → 打球 → 当てはめ（実際の流れ） | 18 | 1.000・1.000 | 1.000 |
| 1〜2 秒 | 検出 → 打球 → 当てはめ | 10 | 1.000・1.000 | 0.500 |

どれも得点した側は 1.000（合成ラリーの最後のショットはいつも相手のコートの中に落ちる）。実動画では、休みの間に
シャトルを拾って打ち返す・隣のコートのシャトルが写るなどで、短い「ラリー」ができることがある（D1 の後に選手の動きで見分ける）。

### 実動画に近い条件の合成ラリー（`smash_speed/synth_clutter.py`）

上の合成ラリーは「シャトルだけが、決まった割合で抜けて見える」観測なので、実動画より精度が高く出る。
`synth_clutter` は、続けて打った合成ラリーに次のものを足した検出と打球音を作り、解析の流れ
（軌道の絞り込み → 打球 → 軌道と初速 → ラリーの区切り → 種類）をそのまま通して測る。

- 検出の抜け：1 コマずつ（12%）、まとめて抜ける区間（1 秒に 0.3 回・0.07〜0.25 秒）、打つ前後に体・ラケットに隠れる（〜30・60 ms）

- 隣のコート（中心が 7.5 m 横）で同じ時間に打っているラリーのシャトルと打球音
- 柔らかいショット（ネット・ショートサーブ・ドロップ）の小さな・拾えない打球音、足音・声などの音
- カメラ：横・遠く（`side`。今までと同じ）、横の近く・低い所（`side_low`。高いショットが画面の上に出る）、
  角の後ろの低い所（`corner_low`）、後ろの高い所（`back_high`）

python -m smash_speed.synth_clutter --bench --clean              # 4 つのカメラで、雑音なし・ありを並べて測る

| 角の後ろ・低い | あり | 0.67 / 0.52 / 0.86 | 23.4% / 5.2%（5） | 0.78 | 0.38 / 1.00 |
| 後ろ・高い | なし | 0.88 / 0.82 / 0.89 | 16.0% / 4.8%（3） | 0.92 | 1.00 / 1.00 |
| 後ろ・高い | あり | 0.63 / 0.48 / 0.79 | 83.5% / 14.8%（12） | 0.58 | 0.75 / 1.00 |

雑音を 1 種類ずつ足すと（横・遠く）、打球の再現率は検出の抜け 0.88・ラケット 0.89・隣のコート 0.96・打球音 0.93・
選手の頭 0.97（足さないときと同じ）で、どれか 1 つなら 0.9 前後に収まる。全部を足すと 0.56 まで落ちる：シャトルの軌道が
抜けで細切れになると、同じ時間に重なった軌道から 1 本を選ぶ所（`shot_list.select_tracks`。点の数の合計が多い組を選ぶ）で、
隣のコートやラケットの軌道に負ける（シャトルの検出のうち選んだ軌道に残るのは 0.84、ほかは 0.99 以上）。
区切りの再現率が下がるのは、打球を見落としたラリーの境目の前後のショットがつながるため。
品質チェック `agent/checks/check_clutter_hits.py` は、角の後ろ・低いカメラで打球の見つけ方だけを測り、今の値より下がらないかを見る。

### ラリーの統計（`smash_speed/rally_stats.py`）

ショットの一覧の出力先に `stats.json`（数字）と `landing.svg`（着地点の分布図）を書き出す（`analyze_video` の最後にも書く）。
前に解析した出力先からは `python -m smash_speed.rally_stats out\IMG_4397_shots` で書き出せる。

- ラリーの長さ：本数・秒（最初に打ってから落ちるまで）の平均・中央値・最長、本数の分布（1〜2・3〜4・5〜8・9〜12・13 本以上）、
  終わり方（in・out・net）と得点した側ごとの数
- ショットの種類：種類ごとの本数・割合・平均と最高の初速（全体と、打った側 h・o ごと）。割合は種類の分かったショットの中で出す
  （不明は本数だけ）。初速が出なかったショットは速さに数えない
- 着地点：「誰も打たなかったら床に着いた所」（種類の判定と同じ）。落ちた側の半面をネットからの深さ（前・中・後）×幅（3 つ）の
  9 つの区画に分けて数える。分布図は種類ごとに 1 面のコート（上から見た図。左が h の側）で、区画の色の濃さが本数、点が 1 本ずつの着地点

### 1 本の動画のレポート（`smash_speed/rally_report.py`）

ショットの一覧の出力先に `report.html` を書き出す（`analyze_video` の最後にも書く）。1 つのファイルで完結する
（外のファイル・ネットを使わない）ので、スマホに送ってそのまま開ける。PDF はブラウザの「印刷」→「PDF に保存」で作る
（印刷用の見た目にしてある）。前に解析した出力先からは `python -m smash_speed.rally_report out\IMG_4397_shots`。

中身は上から、動画の名前・撮った日時・解析した区間、大きな数字（ラリー・ショットの数、いちばん速い初速、ラリーの平均の長さ）、
種類の割合と種類ごとの初速（棒と表。打った側ごとの表は畳んである）、ラリーの長さの分布、着地点の分布図、速いショット 10 本、
ラリーの一覧。画面の明るさ（明るい・暗い）に合わせて色が変わる。

### セッションをまたいだ記録（`smash_speed/history.py`）

出力の場所の下のショットの一覧の出力先（`shot_list.json` と `shots.csv` がある所）をすべて集め、撮った日ごとにまとめて
`history.csv`（1 行 1 日）と `history.html`（スマッシュの初速の最高・平均の推移、種類の割合の変化、日ごとの表）を書き出す。

```powershell
python -m smash_speed.history out      # out\history.csv・out\history.html
```

撮った日は `shot_list.json` の `recorded_at`（動画のタグ。C3 から入る）、なければ動画のファイルの更新日時。同じ日の動画は 1 つにまとめる。
スマッシュの一括解析の出力先（スマッシュだけ）は、種類の割合が偏るので入れない。前に解析した出力先には `recorded_at` がないので、
動画のファイルの日時になる（動画を移した・コピーした日になっていることがある）。

## 実動画（iPhone 17, 4K 30fps）で試した結果

| 動画 | カメラ | 結果 |
|---|---|---|
| IMG_4397（113 s） | 打つ人の後ろ・低め | 25.84 s のスマッシュ：**301.6 km/h（95% 263〜340）**、15 コマ、画面上のずれ 1.3 px。一括解析では打球音 67 個 → 軌道 26 個 → スマッシュらしい 12 個。①だいたいの初速は②で確認した値に対して −10〜+37%（候補による） |
| IMG_4521（151 s） | ネット際の横・低い（0.95 m） | 125.8 s のスマッシュ：**210.8 km/h（95% 194〜228）**、4 コマ、ずれ 15 px（使えるコマが少なく不確か）。一括解析ではスマッシュらしい候補が 4 個と少なく、このスマッシュは「推定が怪しい」に入る |

**時刻のずれの修正（2026-10）**：iPhone の動画は先頭に表示しないフレームがあり、以前の版はそれを含めて時刻を数えていた
（IMG_4521 では全フレームが 0.1 s 遅れ）。また OpenCV はフレーム番号を公称 30 fps で時刻に直して読むため、実際の 29.97 fps と
ずれて、動画の後ろの方で数コマ違うフレームを返すことがあった（IMG_4521 の 125 s 付近で 2 コマ）。どちらも直し、
映像の時刻は音声と同じ「表示時刻」に合わせてある。この修正の前に IMG_4521 で出した値（275 km/h など）は使わないこと。

次に撮るときは「撮影ガイド」のとおり、スマッシュを打つ選手の側方・高い位置から、速いシャッターで撮るのがよい。
