# Badminton Analytics ロードマップ

エージェントは上から順に、状態が `[ ]` の課題を 1 回に 1 つ進める。
状態：`[ ]` まだ ／ `[~]` 途中（次回も続ける） ／ `[x]` 済み ／ `[?]` 確認待ち（`QUESTIONS.md` を見る） ／ `[-]` やめた

課題が 1 回（1〜2 時間）で終わらないときは、`B3a`・`B3b` のように分けてから最初の部分だけ進める。
新しい案は、いちばん下の「エージェントからの提案」に書く（自分で優先度を上げない）。

参考にする既存のツール・研究：Kinovea（動画上の角度・距離の計測）、Hawk-Eye（シャトルの 3 次元軌道）、
TrackNet / TrackNetV3（シャトル検出）、MonoTrack（単眼カメラからのバドミントンの 3 次元軌道）、
ShuttleSet / CoachAI（ショットの種類の分類体系と、ラリー単位の戦術データ）、
姿勢推定（MediaPipe Pose、RTMPose、YOLO-Pose）。

## B. すべてのショットの速度と種類（最優先）

- [ ] **B1 合成データをすべてのショットに広げる**
  `synth.py` にクリア・ドロップ・ドライブ・ロブ・ネット・プッシュ・サーブの軌道（初速・打ち出し角・打点の高さの範囲）を足し、
  1 ラリー分の連続したショットの合成動画を作れるようにする。分類と速度の正解に使う。
- [ ] **B2 すべての打球を見つける**
  今は打球音の後のスマッシュ候補だけ。打球音（オンセット）と、シャトルの軌道の向きが変わる所を組み合わせて、
  動画の中のすべての打球の時刻と打った側を出す。合成ラリーで再現率・適合率を測り、テストを付ける。
- [ ] **B3 ショットごとの軌道と初速**
  スマッシュ用の物理モデルのフィットを、山なりのショット（クリア・ロブ）や遅いショット（ドロップ・ネット）にも使えるようにする。
  飛行平面は「打点 → 次の打点（または着地点）」から決める。合成データで種類ごとの初速の誤差を出す。
- [ ] **B4 ショットの種類の判定（ルール）**
  初速・打ち出し角・打点の高さ・ネットを越える高さ・着地点の深さから、
  スマッシュ／クリア／ドロップ／ドライブ／ロブ／ネット／プッシュ／サーブを判定する。
  分類体系は ShuttleSet を参考にする。合成データで混同行列を出し、`agent/checks/` に精度のチェックを足す。
- [ ] **B5 GUI：ショットの一覧**
  動画を開くとすべてのショットが種類・初速つきで並び、種類で絞り込め、
  1 本を選ぶとその場面とコートの上から見た軌道が出る画面。スマッシュの画面はこの一部にする。
- [ ] **B6 種類の正解ラベルを付ける画面**
  ショットの一覧で種類を手で直せるようにし、その結果を正解ラベルとして保存する（将来の学習データ）。
- [ ] **B7 種類の判定（学習）**
  正解ラベルが 200 本以上たまったら、軌道の特徴量からの分類器（まずは勾配ブースティングなど軽いもの）を学習し、ルールと比べる。
  ラベルが足りなければ `[?]` にして、何本ほしいかを `QUESTIONS.md` に書く。

## エージェントからの提案

（ここに追記する。理由と、どの課題の後にやるとよいかを書く）

- **実動画の基準に「正しい初速」を足す**（A1 の後、B3 の前）：A1 の基準は「今のコードの結果」なので、変わったかどうかは分かるが、
  良くなったか悪くなったかは分からない。240fps の IMG_5096 などで、コマを手で追った初速（またはスピードガン）を正解として基準に足すと、
  解析を変えたときに改善か悪化かを判断できる。
- **IMG_5096 #4（18.7 s）の確認**：古いコードの 82.7 km/h が、今のコードでは 37.0 km/h になる（ほかの差は 3〜23%）。
  使えるコマが 4 個と少なく、スマッシュではない可能性もある。順位表から外すか、候補探しで落とすべきかを B2・B4 のときに見直す。
