# Badminton Analytics ロードマップ

エージェントは上から順に、状態が `[ ]` の課題を 1 回に 1 つ進める。
状態：`[ ]` まだ ／ `[~]` 途中（次回も続ける） ／ `[x]` 済み ／ `[?]` 確認待ち（`QUESTIONS.md` を見る） ／ `[-]` やめた

課題が 1 回（1〜2 時間）で終わらないときは、`B3a`・`B3b` のように分けてから最初の部分だけ進める。
新しい案は、いちばん下の「エージェントからの提案」に書く（自分で優先度を上げない）。

参考にする既存のツール・研究：Kinovea（動画上の角度・距離の計測）、Hawk-Eye（シャトルの 3 次元軌道）、
TrackNet / TrackNetV3（シャトル検出）、MonoTrack（単眼カメラからのバドミントンの 3 次元軌道）、
ShuttleSet / CoachAI（ショットの種類の分類体系と、ラリー単位の戦術データ）、
姿勢推定（MediaPipe Pose、RTMPose、YOLO-Pose）。

## B. すべてのショットの速度と種類（最優先）

- [x] **B1 合成データをすべてのショットに広げる**（`smash_speed/synth_rally.py`。synth.py が長いので分けた）
  `synth.py` にクリア・ドロップ・ドライブ・ロブ・ネット・プッシュ・サーブの軌道（初速・打ち出し角・打点の高さの範囲）を足し、
  1 ラリー分の連続したショットの合成動画を作れるようにする。分類と速度の正解に使う。
- [x] **B2 すべての打球を見つける**（`smash_speed/hits.py`、チェックは `agent/checks/check_hits.py`）
  今は打球音の後のスマッシュ候補だけ。打球音（オンセット）と、シャトルの軌道の向きが変わる所を組み合わせて、
  動画の中のすべての打球の時刻と打った側を出す。合成ラリーで再現率・適合率を測り、テストを付ける。
  （入力は動画全体のシャトルの検出結果。実動画の全コマを検出して `find_hits` に渡す流れは B5 で GUI とつなぐ）
- [x] **B3 ショットごとの軌道と初速**（`smash_speed/shot_fit.py`、チェックは `agent/checks/check_shot_speeds.py`）
  スマッシュ用の物理モデルのフィットを、山なりのショット（クリア・ロブ）や遅いショット（ドロップ・ネット）にも使えるようにする。
  飛行平面は「打点 → 次の打点（または着地点）」から決める。合成データで種類ごとの初速の誤差を出す。
  （横の合成ラリーで全体 1.3〜2.7%。サーブ・ネットなど短いショットと、角から撮ったときが弱い。実動画とつなぐのは B5）

  スマッシュ／クリア／ドロップ／ドライブ／ロブ／ネット／プッシュ／サーブを判定する。

  （合成の横のカメラで 0.98〜1.00。しきい値は合成の範囲から決めたので、実動画の精度は B6 のラベルで測り直す）

## E. フォームと姿勢

この章では、スマホ動画からストロークのフォームを数値にする。主な対象はフォアハンドのハイクリア、スマッシュは発展。
撮影の想定：側方からスマホ 1 台（ラケットを持つ腕の側、打球方向に直交、距離 6〜8 m、高さ 1.2〜1.5 m、水平）、1080p・60fps、音声あり。
**データの決まり**：この章で使ってよい動画は、合成データと、`videos_dir` にある本人の動画だけ。ほかの人の動画・姿勢のデータは、
人が別に決めるまで読まない・書き出さない・コミットしない。特徴量の定義は、あとで人が説明できるよう、式と理由を `docs/pose_features.md` に書く。

（E1〜E7 は、実動画のいらない所までクラウドのセッションが進めた（合成の骨格・偽物のモデルで確かめた）。残りは各課題の「残り」に書いた、
デスクトップで実際のモデル・実動画で確かめる所。式と理由・合成での精度は `docs/pose_features.md`）

- [~] **E1 姿勢推定の導入**：A2 の結果をもとに、姿勢推定のモデルを選んで入れる（ライセンスを確認する）。
  候補は RTMPose（rtmlib、ONNX Runtime + DirectML で GPU）と MediaPipe Pose。両方を入れて比べられるようにし、
  手で付けた関節の位置（約 200 コマ。付けるのは人。付け方と保存の形を決め、読み込みと PCK などの精度の計算を作る）と比べて採用を決める。
  信頼度の低い関節（隠れた非利き腕など）を外す処理も入れる。
  - 済み（`smash_speed/pose.py`）：COCO 17 点にそろえたモデルの差し替えの形、RTMPose（rtmlib のセッションを `accel.make_session` に載せ替えて DirectML）、
    MediaPipe（33 点 → 17 点）、打つ人の選び方、信頼度の低い関節を欠けにして短い欠けを埋める処理、手で付けた関節の CSV の形と PCK@0.2（胴体の長さ）、
    `python -m smash_speed.pose estimate|pck`。合成の骨格（`synth_pose.py`）の偽物のモデルで確かめた。MediaPipe はクラウドの CPU で動くことだけ確かめた。
  - 残り（デスクトップ）：RTMPose の重みの取得と DirectML での実行（クラウドでは配布元に届かず試せなかった）、人が付けた約 200 コマで両方の PCK を出して採用を決める。
- [~] **E1b 前処理**：ショット単位の切り出し（打点の前 1.0 秒〜後 0.5 秒。打点の時刻は打球音のピーク（`shot_fit.audio_hit_times`）と
  手首の速さの最大を合わせて決め、手で付けた打点のコマとの誤差を測れるようにする）、顔のぼかし、左利きの左右反転、
  腰の中点を原点にして胴体の長さ（肩〜腰）で割る正規化。
  - 済み（`smash_speed/pose_prep.py`）：すべて。打点は手首の最大の ±0.15 秒の打球音 − 距離 ÷ 音速、音がなければ手首の最大 + 差（`calibrate_wrist_offset`）、
    誤差は `impact_errors`。手首の最大は打点の約 0.03 秒前で、そのまま使うと肘の角度が 15° ほど小さく出ることを合成で確かめた。
  - 残り（デスクトップ）：実動画で、手で付けた打点のコマとの誤差を測り、音がないときの差（`wrist_offset_s`）を決める。
- [x] **E2 打点の瞬間の姿勢**：打点の高さ、肘・肩・膝の角度、体の向きを出し、ショットの一覧に足す。

- [~] **E6 クリアの打球の結果**：側方の撮影で、シャトルの初速・打ち出し角・最高点・落ちた所の深さを出す（B3 の当てはめを使う）。

## エージェントからの提案

（ここに追記する。理由と、どの課題の後にやるとよいかを書く）

- **実動画の基準に「正しい初速」を足す**（A1 の後、B3 の前）：A1 の基準は「今のコードの結果」なので、変わったかどうかは分かるが、
  良くなったか悪くなったかは分からない。240fps の IMG_5096 などで、コマを手で追った初速（またはスピードガン）を正解として基準に足すと、
  解析を変えたときに改善か悪化かを判断できる。
- **IMG_5096 #4（18.7 s）の確認**：古いコードの 82.7 km/h が、今のコードでは 37.0 km/h になる（ほかの差は 3〜23%）。
  使えるコマが 4 個と少なく、スマッシュではない可能性もある。順位表から外すか、候補探しで落とすべきかを B2・B4 のときに見直す。
- **合成ラリーに雑音・人・画面の外を足す**（B2 の後、B5 の前）：B2 の打球の見つけ方は、横から撮った合成ラリーでは
  ほぼ 100% だが、後ろから撮った 30 fps では適合率が 0.94 ほどに下がる（遠くへ飛ぶ・近づくシャトルの見かけの加速を
  打球と間違える）。実動画では検出の抜け・誤検出・画面の外での打球が多いので、`render_cluttered_video` のような
  ラリー版の合成動画（人・隣のコート・低いカメラ）で測り直すと、実動画での精度に近い数字になる。
- **サーブ（ラリーの最初のショット）の打点の時刻**（B3 の後、B5 の前）：B3 では打点の時刻を前後の軌道が交わる時刻に
  直して速いショットの誤差を減らしたが、サーブは前の軌道がないので直せず、30 fps・軌道だけで 10.8% ずれる。
  打球音の遅れを当てはめた打点の位置からの距離で引き直す（スマッシュの解析と同じ）か、D1 の選手の位置から打点を決めると良くなる。
- **角・低いカメラでの短いショット**（B3 の後）：実動画に近い角・低い位置のカメラでは、ドライブ・ネットが 9〜11%、
  サーブが 15〜19% ずれる（横のカメラでは 2〜7%）。飛行平面の補正の大きさ（`plane_sigma_deg`）を飛行の長さで変える、
  D2 の選手の足元を打点の手がかりにする、などで改善できそう。
- **合成ショットの種類の範囲を重ねる**（B4 の後、B6 の前）：B4 のしきい値は `SHOT_PROFILES` の範囲から決めたので、
  合成データでは種類がほぼ重ならず、正解率が 0.98〜1.00 と高く出すぎる。実際には速いドロップと遅いスマッシュ、
  高めのドライブと低いロブ、打点の高いプッシュとドロップなどが重なる。範囲を少し広げて重ねた「あいまいな」合成ラリーを
  作ると、境目での間違い方（どの種類と混ざるか）を実動画の前に見られる。ラベルが集まったら B7 で境目を学習で決める。
- **実動画の打点の奥行き**（B5a3 の後、B5c か D3 のころ）：IMG_4397 の 94.9 s のスマッシュは、当てはめた打点が
  x = −5.62 m と基準の打点（−2.84 m）より 3 m 後ろに出て、410 km/h（基準 351）になる。見えている 9 コマ（30 fps）だけでは
  奥行きが決まりにくい。D1・D3 の選手の足元から打点の位置の事前分布を入れるか、飛んできた軌道（93.29 s の当てはめ。
  今は 209 km/h のロブと出ていて怪しい）とのつなぎ方を見直すと良くなりそう。どちらが正しいかを決めるには、
  正しい初速の基準（上の提案）が要る。
- **同じ側が続く打球**（B5a3 の後）：IMG_4397 の 86.14 s・86.41 s のように、同じ側が 2 回続けて打ったと判定される所が
  残っている（どちらかは打球ではない）。軌道の重なりを選び直した後の打球の見つけ方（`find_hits`）を、実動画で見直す。
- **GUI からレポート・記録を開く**（B5c2 の後）：C3 の `report.html` と C4 の `history.html` は書き出すだけで、GUI からは開けない。
  ショットの一覧の画面に「レポートを開く」、左のメニューに「記録の推移」（`history.write_history` を出力の場所で動かす）を足すとよい。
  C 章はクラウドのセッションが進めたので、B5c2 の `shots.js`・`server.py` と取り合わないように入れていない。
- **ラリーの区切りに選手の動きを足す**（D1・D2 の後）：C1 は打球の間隔・着地・シャトルが飛んでいるかだけで区切る。
  休みの間にシャトルを拾って打ち返す・隣のコートのシャトルで短い「ラリー」ができたら、選手がサーブの位置で止まったか・
  コートの外へ歩いたかで見分ける。
- **「打球ではない」のラベル**（B6b の後、B7 の前）：実動画では、隣のコートのシャトルや、同じ側が続けて打ったと出る所
  （上の「同じ側が続く打球」）のように、打球でないものが一覧に混ざる。今の正解ラベルは 8 つの種類だけなので、
  `shot_labels.csv` に「打球ではない」を足すと、B7 で打球の見つけ方の誤りも学習・測定できる（`SHOT_TYPES` には入れず、ラベルだけに持つ）。
- **合成ラリーに外・ネットで終わるラリーを足す**（C1 の後）：合成ラリーの最後のショットはいつも相手のコートの中に落ちるので、
  終わり方（out・net）と得点した側の判定は合成では確かめられていない。狙う着地点をときどき線の外・ネットの手前にすると測れる。
